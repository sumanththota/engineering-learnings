# Hand-roll the future MCP server; don't adopt a generic vault-search tool

Existing MCP servers for markdown vaults (`markdown-vault-mcp`, `vault-search-mcp`) solve a bigger, more generic problem than this repo has: arbitrary long-form notes, heading-level chunking, SQLite FTS5 plus embeddings plus Reciprocal Rank Fusion. They have no concept of this repo's domain model — Specific vs Principle, Corroboration derived from `links`, Superseded deprioritization — so that logic would have to be bolted on top of someone else's engine rather than living naturally in a small purpose-built server. We'll instead wrap `INDEX.json` directly with two tools, `search_learnings` and `add_learning`, using a plain field-weighted linear scan (exact/substring match on `tags`/`project`/`id`, boosted by Corroboration, penalized for `superseded_by`); a dataset of dozens to low hundreds of entries doesn't justify database-grade indexing. Until that server exists, an agent reads `INDEX.json` directly and filters it in-context — the same logic the future server will wrap, so there's no rework when it's built (per ADR 0001).
